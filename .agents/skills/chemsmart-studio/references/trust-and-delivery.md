# Trust, validation, and delivery

## Evidence discipline

- Base scientific and product claims on observable state, generated contracts, deterministic parser output, receipts, and package inspection.
- Record source HEAD, submodule pin, lock hash, command, timestamp, duration, and bounded failure details without secrets.
- Report passed, failed, unavailable, and intentionally untested gates separately.
- Do not claim model superiority, autonomous scientific judgment, calculation correctness, production readiness, signing, or notarization without direct passing evidence.
- Keep hidden reasoning, credentials, private provider turns, unrestricted paths, and unpublished structures out of receipts, fixtures, issues, and release notes.

## Validation cadence

1. Run `./dev/studio doctor --json`, state/provenance checks, schema meta-validation, and generated-model freshness when their area changes.
2. Run focused TypeScript/Python tests for the changed authority and inspect the real UI for visual, focus, resize, keyboard, or accessibility behavior.
3. Run broad repository gates once after a coherent milestone. Stop duplicate Electron/sidecar processes first and avoid parallel builds that multiply memory use.
4. Re-run only failed gates and checks affected by the repair. Do not repeat an unchanged successful full gate.
5. Before commit, run scoped formatting, whitespace, generated-diff, lock, and secret-safe staged checks.

## Workflow acceptance

- Verify project create/open/import/save/switch/restart, draft apply/discard/undo/redo, Agent/Console pane recovery, and focus preservation.
- Verify tool streaming/grouping, denial, cancellation, stale approval, one terminal event, and no process after denial.
- Verify durable run frame counts, replay binding, final decision recovery, project rebind, and zero orphan sidecar processes.
- Audit packages for exact version/architecture, Protocol v2 identity, portable Python bridge, notices/source link, immutable app contents, and absence of credentials or training data.
- Do not start real chemistry, submit HPC work, publish, push, sign with an identity, or replace an installed application without explicit authorization.

## Release language

- Call an ad-hoc-signed, non-notarized build an internal research build or internal stable release only when its named acceptance evidence passes.
- Reserve public macOS distribution readiness for Developer ID signing, hardened runtime verification, notarization, stapling, and clean-machine acceptance.
- Distinguish source readiness, focused feature evidence, package smoke, internal release, and public production readiness. None implies the next.
